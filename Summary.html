Inkwell — Technical Deep Dive

A complete walkthrough of every architectural decision, data flow, and implementation pattern in this full-stack publishing platform — a Medium/Ghost/Substack-style product built end to end.

Next.js 15 TypeScript Prisma 6 PostgreSQL NextAuth v5 Zod Tiptap Tailwind CSS v4 shadcn/ui Groq AI Resend UploadThing

Project Overview

Inkwell is a full-stack publishing platform — write, publish, and discover long-form articles, with real accounts, comments, notifications, and an admin panel behind it. It's built as a genuine multi-role product: readers, writers, moderators, and admins each get different capabilities enforced at every layer, not just hidden in the UI.

What the system does
  • Public site: Home page (featured/latest/trending posts, categories, featured writers), Discover (search/sort/filter), category listings, public author profiles (/@username), article pages with comments.
  • Writer tools: A Tiptap-based editor with autosave, AI-assisted titles/excerpts/tags, real image upload, a "Following" feed, reading lists, a personal dashboard with stats.
  • Admin panel (/admin): Live stats + posts-per-day chart, user management (role change, ban/unban), post management (status, feature toggle), and a moderation queue for reports — every mutation writes an audit log entry.
Key architectural philosophy: There are no REST API routes for data mutations. Everything goes through Next.js Server Actions — functions that run on the server but are called directly from client components, eliminating fetch() calls to internal API routes. The only real API routes are the two things that genuinely need one: the NextAuth handler and the UploadThing handler.

Next.js 15 App Router

Every file in app/ is a React Server Component (RSC) by default. Data-fetching pages call Prisma directly; interactive pieces opt into client rendering explicitly.

Server Components vs Client Components

Server Component (default)
  • Runs only on the server — never shipped to the browser as JS
  • Can await Prisma calls directly — no useEffect, no internal fetch()
  • Example: src/app/(main)/page.tsx — the home page directly calls getFeaturedPosts(), getLatestPosts(), getFeaturedWriters() in parallel with Promise.all
Client Component ("use client")
  • Server-rendered for the initial HTML, then hydrated in the browser
  • Can use hooks, event handlers, browser APIs
  • Examples: PostEditor (Tiptap needs the DOM), CommentForm, FollowButton, the admin tables

Server Actions

Every mutation in this project — creating a comment, liking a post, saving a draft, following a user, banning an account — is a function marked "use server", called directly from a client component like a normal async function call.

The shape every action follows

// src/features/comments/actions/create-comment.action.ts
"use server";

export async function createCommentAction(input: CreateCommentInput) {
  // 1. Auth check — session read server-side, never trusted from the client
  const session = await auth();
  if (!session?.user) throw new Error("You must be signed in to comment.");

  // 2. Validate input with Zod — never trust the shape of client data
  const { postId, content, parentId } = createCommentSchema.parse(input);

  // 3. Business logic in a transaction — see Transactional Mutations
  const comment = await db.$transaction(async (tx) => {
    const created = await tx.comment.create({ data: { postId, authorId: session.user.id, content, parentId } });
    await tx.post.update({ where: { id: postId }, data: { commentCount: { increment: 1 } } });
    // ...also creates a Notification row here, see Notifications System
    return created;
  });

  // 4. Invalidate the article page's cache
  revalidatePath(`/articles/${post.slug}`);
  return comment;
}

Calling it from a client component

// comment-form.tsx — react-hook-form + useTransition
function onSubmit(values: CreateCommentInput) {
  startTransition(async () => {
    try {
      await createCommentAction(values); // ← looks local, runs on the server
      form.reset();
    } catch (error) {
      toast.error(error instanceof Error ? error.message : "Failed to post comment.");
    }
  });
}

Every action in the codebase follows this same skeleton: auth → validate → mutate (transaction if multiple writes) → revalidate. Once that shape is familiar, reading any new action takes seconds.

Authentication Flow

NextAuth v5 with two providers: a Credentials provider (email/password) and optional Google/GitHub OAuth. Sessions are JWTs stored in an httpOnly cookie — no database session lookup on every request.

Credentials login step by step

1. Form submits
→
email + password to NextAuth's signIn("credentials")
2. authorize() runs
→
Zod validates shape → rate-limit check → DB lookup → bcrypt.compare()
3. jwt() callback
→
id, role, and username (from Profile) added to the token
4. session() callback
→
id/role/username copied from token onto session.user
5. Cookie signed
→
Encrypted with AUTH_SECRET, stored httpOnly

The authorize() function, including rate limiting

// src/server/auth/config.ts
async authorize(rawCredentials) {
  const parsed = credentialsSchema.safeParse(rawCredentials);
  if (!parsed.success) return null;

  const { email, password } = parsed.data;

  // 5 attempts / 15 min, keyed per email — not global, not per-IP
  if (!checkRateLimit(`login:${email.toLowerCase()}`, LOGIN_RATE_LIMIT)) {
    return null;
  }

  const user = await db.user.findUnique({ where: { email } });
  if (!user?.passwordHash) return null;

  const isValid = await bcrypt.compare(password, user.passwordHash);
  if (!isValid) return null;
  if (user.isBanned) return null;

  return { id: user.id, name: user.name, email: user.email, image: user.image, role: user.role };
}
Why rate-limit inside authorize(), not in front of it? Rejecting inside authorize() reuses NextAuth's existing "invalid credentials" response path — the client gets the same generic failure whether the password was wrong or the account is locked out. That's deliberate: a distinct "you're rate-limited" response would leak information about which accounts exist and are being targeted.

Middleware & Route Protection

Middleware runs at the Edge, before any page or server action executes. It's the first and cheapest gate.

// src/middleware.ts
import { auth } from "@/server/auth/edge";
import { NextResponse } from "next/server";

const PROTECTED_PREFIXES = ["/dashboard", "/settings", "/new-post", "/admin"];
const ADMIN_PREFIXES = ["/admin"];

export default auth((req) => {
  const { pathname } = req.nextUrl;
  const isProtected = PROTECTED_PREFIXES.some((p) => pathname.startsWith(p));
  const isAdminOnly = ADMIN_PREFIXES.some((p) => pathname.startsWith(p));

  if (!isProtected) return NextResponse.next();

  if (!req.auth) {
    const loginUrl = new URL("/login", req.nextUrl.origin);
    loginUrl.searchParams.set("callbackUrl", pathname);
    return NextResponse.redirect(loginUrl);
  }

  if (isAdminOnly && req.auth.user.role !== "ADMIN") {
    return NextResponse.redirect(new URL("/", req.nextUrl.origin));
  }

  return NextResponse.next();
});

export const config = {
  matcher: ["/dashboard/:path*", "/settings/:path*", "/new-post/:path*", "/admin/:path*"],
};

Two things happen in one pass: is the user authenticated at all, and — for /admin specifically — do they have the right role. A signed-in reader hitting /admin gets redirected home, not to login (they're already authenticated; they're just not authorized).

Why @/server/auth/edge and not the main auth module? See the Auth Split Pattern below — middleware runs in the Edge runtime, which can't load bcryptjs or the Prisma adapter.

Prisma ORM & Database Schema

The Prisma singleton pattern

// src/server/db/client.ts
const globalForPrisma = globalThis as unknown as { prisma?: PrismaClient };

export const db =
  globalForPrisma.prisma ?? new PrismaClient();

if (process.env.NODE_ENV !== "production") globalForPrisma.prisma = db;
Why the singleton? Next.js dev's Hot Module Replacement re-evaluates modules on every save. Without this pattern, each HMR cycle instantiates a new PrismaClient — and Postgres has a connection-pool limit that gets exhausted quickly. Storing the instance on globalThis (which HMR doesn't re-evaluate) makes the client survive file saves.

A few schema decisions worth knowing

model Comment {
  id       String @id @default(cuid())
  content  String @db.Text
  postId   String
  authorId String

  parentId String?
  parent   Comment?  @relation("CommentReplies", fields: [parentId], references: [id], onDelete: Cascade)
  replies  Comment[] @relation("CommentReplies")

  isEdited  Boolean @default(false)   // set true on edit, no separate edit-history table
  isDeleted Boolean @default(false)   // soft delete — see Comments & Soft Delete section

  @@index([postId])
  @@index([parentId])
}

Nesting is intentionally capped at one level — replies don't themselves have replies. A self-relation with onDelete: Cascade means deleting a comment at the DB level would cascade-delete its replies; the app never hard-deletes a comment with live replies for exactly that reason (see the Comments section).

model PostTag {
  postId String
  tagId  String
  @@id([postId, tagId])   // composite primary key — no separate id column, no duplicate rows possible
}

Many-to-many join tables (PostTag, PostCategory) use a composite primary key on the two foreign keys instead of their own id. It's both the natural uniqueness constraint and the key Prisma's upsert/delete calls target directly (postId_tagId: { postId, tagId }).

Zod Validation

Every server action validates its input with Zod before touching the database — the schema is the single source of truth for both runtime validation and the TypeScript type.

// src/features/comments/schemas/comment.schema.ts
export const createCommentSchema = z.object({
  postId:  z.string().cuid(),
  content: z.string().trim().min(1, "Comment can't be empty").max(5000),
  parentId: z.string().cuid().optional(),
});

// Type is inferred — one source of truth for validation and types
export type CreateCommentInput = z.infer<typeof createCommentSchema>;

Server actions call .parse() (throws on failure, caught by the client's try/catch around the action call) rather than .safeParse() — consistent with the try/catch + toast error pattern used throughout the client components here, instead of field-level form errors returned from every action.

React Hook Form + Zod resolver

  defaultValues: { postId, parentId, content: "" },
});

Editor & Content Pipeline

Why HTML is sanitized server-side before rendering

Tiptap's native output is HTML (plus a JSON document tree kept alongside it for reloading the editor state). That HTML is rendered to real readers with dangerouslySetInnerHTML — which means it has to be untrusted by default and cleaned up before it ever reaches the browser.

// src/lib/render-content.ts
const processor = unified()
  .use(rehypeParse, { fragment: true })   // HTML string → AST
  .use(rehypeSlug)                     // headings get id="..." for the table of contents
  .use(rehypeSanitize, schema)         // strips scripts/handlers/unknown tags — XSS defense
  .use(rehypeHighlight)                // syntax-highlights <pre><code> blocks
  .use(rehypeStringify);              // AST → HTML string

export async function renderPostHtml(rawHtml: string): Promise<string> {
  const file = await processor.process(rawHtml);
  return String(file);
}
The sanitize step is what makes dangerouslySetInnerHTML safe here. Without rehypeSanitize, any HTML a writer's editor session produced (or anything an attacker got into the JSON/HTML via a compromised client) would render verbatim — including <script> tags. The schema extends rehype's default allowlist only to add img and a few explicit attributes (className, id, link target/rel) — nothing else gets through.

Resuming a draft

/new-post/[id] loads a post owned by the current user and hands both the saved JSON and raw HTML to the editor:

const post = await db.post.findUnique({ where: { id }, include: { tags: { include: { tag: true } } } });
if (!post || post.authorId !== session.user.id) notFound();

return (
  <PostEditor
    postId={post.id}
    initialTags={post.tags.map(({ tag }) => tag.name)}
    // falls back to raw HTML if no saved Tiptap JSON exists (true for older/seeded posts)
    initialContent={(post.contentJson as JSONContent | null) ?? post.content}

Autosave — tracking the created post id

The editor creates a draft Post row on the first save and must reuse that same id on every subsequent autosave tick, not create a new post every ~8 seconds. It tracks the id in both state (for re-renders) and a ref (so the debounced autosave closure always reads the current value, not a stale one from when the effect was set up):

const currentPostIdRef = useRef(currentPostId);
currentPostIdRef.current = currentPostId;

async function persistDraft() {
  const result = await savePostDraftAction({ postId: currentPostIdRef.current, ... });
  if (!currentPostIdRef.current) {
    currentPostIdRef.current = result.id;
    setCurrentPostId(result.id);   // only set once, on the very first save
  }
  return result;
}

AI Writing Assist

An "AI Assist" popover in the editor generates title suggestions, an excerpt, and tag suggestions from the current draft, using Groq's openai/gpt-oss-120b.

// src/server/ai/client.ts
export async function generateCompletion({ system, prompt, maxTokens = 400 }): Promise<string> {
  const response = await fetch(GROQ_URL, {
    method: "POST",
    headers: { Authorization: `Bearer ${apiKey}`, "Content-Type": "application/json" },
    body: JSON.stringify({
      model: "openai/gpt-oss-120b",
      messages: [{ role: "system", content: system }, { role: "user", content: prompt }],
      max_tokens: maxTokens,
      reasoning_effort: "low",   // see callout below
      temperature: 0.7,
    }),
  });
  // ...error handling, extract data.choices[0].message.content
}
Reasoning models silently return nothing if you don't budget for reasoning tokens. The first real test call used max_tokens: 10 and got back an empty string — not an error, just "". gpt-oss-120b is a reasoning model: it spends tokens on a hidden chain-of-thought before writing the visible answer, and a too-small token budget gets entirely consumed by that hidden reasoning, leaving nothing for the actual output. The fix was two things together: setting reasoning_effort: "low" to cap how much it reasons, and giving each call a realistic max_tokens (300–400) instead of a stingy one.

Why every AI action shares one shape

export async function suggestTagsAction(input) {
  await requireUser();                                    // auth gate
  const plainText = truncateWords(stripHtml(contentHtml)); // bound the prompt size
  if (plainText.length < 20) throw new Error("Write a bit more first.");

  const raw = await generateCompletion({ system: "...5 short tags, comma-separated...", prompt, maxTokens: 100 });

  // Post-process a free-text model response into a clean, bounded array —
  // never trust the model to perfectly follow the "5 tags, comma-separated" instruction
  const tags = raw.split(",").map((t) => t.trim()).filter(Boolean).slice(0, 5);
  if (tags.length === 0) throw new Error("AI didn't return anything usable — try again.");
  return { tags };
}

Titles, excerpts, and tags each follow the identical shape: require a signed-in user, strip/truncate the draft's HTML to plain text so the prompt stays bounded, call Groq with a task-specific system prompt, then parse the model's free-text response defensively rather than trusting it returned exactly the requested format.

Notifications System

Follows, comments, replies, and likes all notify — in-app always, email conditionally based on the recipient's per-type setting (emailOnComment, emailOnLike, emailOnFollow).

Replies notify the comment's author, not the post's author

const recipient = parent ?? { authorId: post.authorId, author: post.author };
if (recipient.authorId !== session.user.id) {
  await tx.notification.create({
    data: {
      type: parent ? "COMMENT_REPLY" : "COMMENT",
      message: parent
        ? `${session.user.name} replied to your comment on "${post.title}"`
        : `${session.user.name} commented on your post "${post.title}"`,
      link: `/articles/${post.slug}`,
      recipientId: recipient.authorId,
      actorId: session.user.id,
    },
  });
}

If replies always notified the post author, a long comment thread would spam the post's author with every back-and-forth reply that has nothing to do with them. Routing the notification to the immediate parent comment's author instead keeps it relevant — and the same if (recipient.authorId !== session.user.id) guard prevents self-notifying when you reply to your own comment or like your own post.

Email sending never blocks or fails the underlying action

export async function sendCommentNotificationEmail(params) {
  try {
    await resend.emails.send({ ... });
  } catch (error) {
    console.error("Failed to send comment notification email", error);
    // deliberately swallowed — a broken email provider must never break commenting
  }
}

Comments & Soft Delete

Comments support one level of nested replies, editing, and deletion — but deletion has to account for the fact that a deleted comment might still have live replies underneath it.

The tombstone problem

The Comment model already had isDeleted and isEdited columns from the original schema design, unused until this feature. A naive delete — just filtering isDeleted: false everywhere — would make a deleted top-level comment disappear from the query entirely, silently orphaning any replies still nested under it (they'd never be fetched, since they only come back as part of their parent's include).

// src/features/comments/services/comment.service.ts
export async function getCommentsForPost(postId: string) {
  const comments = await db.comment.findMany({
    where: { postId, parentId: null },   // no isDeleted filter here —
    include: { author: true, replies: { include: { author: true } } },
  });

  // A deleted top-level comment is dropped entirely unless it still has live
  // replies underneath it — in which case it renders as a tombstone so the
  // replies stay reachable.
  return comments.filter(
    (c) => !c.isDeleted || c.replies.some((r) => !r.isDeleted)
  );
}

The UI checks comment.isDeleted and renders [deleted] in place of the content and author actions, while still rendering any live replies underneath. Once every reply is also deleted, the parent naturally drops out of the filtered result on the next fetch — no separate cleanup job needed.

This is a small, self-contained example of a broader idea: soft-delete flags aren't just "hide it" — they force you to think through every place that data is still structurally referenced by something else that's still alive.

Tag Sync — Diffing Instead of Replacing

The editor autosaves roughly every 8 seconds. A tag list attached to a draft could naively be synced by deleting every PostTag row and recreating them from the current tag list on every save — but that would increment/decrement every tag's usageCount on every autosave tick, even when the tags haven't changed at all.

async function syncPostTags(tx, postId, rawTags) {
  const names = [...new Set(rawTags.map((t) => t.trim().toLowerCase()))].slice(0, 10);

  const current = await tx.postTag.findMany({ where: { postId }, include: { tag: true } });
  const currentNames = new Set(current.map((pt) => pt.tag.name));
  const nextNames = new Set(names);

  const toRemove = current.filter((pt) => !nextNames.has(pt.tag.name));  // only what actually left
  const toAdd = names.filter((n) => !currentNames.has(n));           // only what's genuinely new

  for (const pt of toRemove) {
    await tx.postTag.delete({ where: { postId_tagId: { postId, tagId: pt.tagId } } });
    await tx.tag.update({ where: { id: pt.tagId }, data: { usageCount: { decrement: 1 } } });
  }
  for (const name of toAdd) {
    const tag = await tx.tag.upsert({
      where: { name },
      update: { usageCount: { increment: 1 } },
      create: { name, slug: slugify(name), usageCount: 1 },
    });
    await tx.postTag.create({ data: { postId, tagId: tag.id } });
  }
}

Diffing against the current state means an autosave tick where nothing about the tags changed does zero tag writes. Tag names are lowercased before comparison so "JavaScript" and "javascript" collapse to one tag instead of silently creating duplicates.

Rate Limiting

A deliberately simple in-memory sliding-window limiter — no external store, resets on server restart, doesn't share state across instances. Enough to blunt casual brute-forcing and signup spam on a single-instance deployment; not a substitute for Upstash/Redis at real scale.

// src/lib/rate-limit.ts
const attempts = new Map<string, { count: number; resetAt: number }>();

export function checkRateLimit(key: string, { max, windowMs }): boolean {
  const now = Date.now();
  const entry = attempts.get(key);

  if (!entry || entry.resetAt <= now) {
    attempts.set(key, { count: 1, resetAt: now + windowMs });
    return true;
  }
  if (entry.count >= max) return false;
  entry.count += 1;
  return true;
}

Signup5 per hoursignup:{ip} — from x-forwarded-for
Verifying a rate limit actually works is harder than it sounds — a wrong password always returns the same generic failure whether or not the limiter fired. The real proof was a 6th login attempt using the correct password still failing after 5 failed ones, while a different account logged in normally at the same time — confirming it was the limiter blocking (not a credentials bug) and that it's scoped per-email (not a global lockout).

Media Upload

Cover images and inline editor images upload through UploadThing rather than being stored as base64 or on the app server's filesystem.

// src/server/uploadthing/core.ts
export const ourFileRouter = {
  imageUploader: f({ image: { maxFileSize: "4MB", maxFileCount: 1 } })
    .middleware(async () => {
      const session = await auth();
      if (!session?.user) throw new UploadThingError("You must be signed in to upload images.");
      return { userId: session.user.id };   // available in onUploadComplete
    })
    .onUploadComplete(async ({ metadata, file }) => {
      return { uploadedBy: metadata.userId, url: file.ufsUrl };
    }),
} satisfies FileRouter;

The auth check lives in .middleware(), which runs before UploadThing issues a presigned upload URL — an unauthenticated request is rejected before any URL to write to exists, not just hidden behind a disabled button client-side. A "paste a URL instead" fallback exists alongside the upload button for both the cover image and inline images.

Full Data Flow — Publishing a Post

1. Client — PostEditor autosaves, then Publish is clicked

The editor has already been autosaving the draft every ~8s via savePostDraftAction. Clicking Publish calls persistDraft() one final time (to flush anything since the last tick), then calls publishPostAction({ postId }).

2. Server Action — publishPostAction()

① auth() reads the session. ② Ownership check — the post's authorId must match. ③ Validates the post has a title and content. ④ Sets status: "PUBLISHED" and publishedAt: new Date(). ⑤ Generates the excerpt from content if none was set manually.

3. Cache invalidation

revalidatePath is called for the new article URL, the author's profile, the home page, and discover — every place the newly-published post now needs to appear with fresh data.

4. Client response

The action returns the post's slug. The client shows a success toast and router.pushes to /articles/[slug] — the freshly published, sanitized, syntax-highlighted article, live.

The Auth Split Pattern

NextAuth's config has to work in two different runtimes: the Edge runtime (middleware) and the Node.js runtime (server actions, server components). The problem: bcryptjs and Prisma's adapter both need Node.js APIs the Edge runtime doesn't have.

FileRuntimeContainsUsed in
edge-config.ts Edge Session/JWT shape, pages config, empty providers: []. No Prisma adapter, no bcrypt. server/auth/edge.ts → middleware.ts only
config.ts Node.js Full config — Prisma adapter, Credentials provider (bcrypt), Google/GitHub OAuth, the jwt() callback that reads the user's Profile server/auth/index.ts → server actions, server components 
// server/auth/edge.ts
import NextAuth from "next-auth";
import { edgeAuthConfig } from "@/server/auth/edge-config";
export const { auth } = NextAuth(edgeAuthConfig);   // used only by middleware.ts

// server/auth/index.ts
import NextAuth from "next-auth";
import { authConfig } from "@/server/auth/config";
export const { handlers, auth, signIn, signOut } = NextAuth(authConfig);   // everywhere else

Both configs share the same session() callback shape (copying id/role/username onto session.user) so a session object read in middleware and one read in a server action look identical to calling code — the split is invisible outside these two files.

Optimistic UI

Likes, bookmarks, and follows update the UI immediately, then confirm against the server in the background — with rollback if the action actually fails.

const [liked, setLiked] = useState(initialLiked);
const [isPending, startTransition] = useTransition();

function handleLike() {
  if (!isAuthenticated) { setShowAuthDialog(true); return; }

  const previous = liked;
  setLiked(!liked);              // 1. flip immediately — no spinner, no wait

  startTransition(async () => {
    try {
      await toggleLikeAction({ postId });
    } catch {
      setLiked(previous);       // 2. roll back on failure
      toast.error("Something went wrong.");
    }
  });
}

Unauthenticated users get a centered "Sign in required" dialog instead of the toggle firing at all — a deliberate UX choice over a silently failing click, and over a corner toast easy to miss.

Transactional Mutations

db.$transaction() wraps every mutation that touches more than one table, so the database is never left in a partial state.

ActionWhat's inside the transaction
Create commentInsert the comment + increment post.commentCount + create a Notification
Delete commentSet isDeleted: true + decrement post.commentCount
Toggle likeCreate/delete the Reaction + increment/decrement post.likeCount + notification on like only
Toggle followCreate/delete the Follow row + create a FOLLOW notification
Save draft tagsDiff-add/remove PostTag rows + increment/decrement each Tag.usageCount
Why it matters here specifically: if incrementing commentCount failed after the comment row itself was already committed (e.g. a crash between the two statements without a transaction), the displayed comment count would silently drift from the real count forever — nothing would ever notice or self-correct. Wrapping both writes in one transaction makes that drift structurally impossible instead of just unlikely.

Interview Q&A — Next.js

Why does this project have almost no API routes?
Every mutation is a Server Action instead — a function marked "use server" that Next.js turns into an auto-generated endpoint, callable directly from a client component like a normal function. The only two real API routes in the codebase are api/auth/[...nextauth] (NextAuth needs a route handler to receive OAuth callback redirects) and api/uploadthing (UploadThing's client SDK needs an endpoint to negotiate the upload). Everything else — creating a comment, liking a post, banning a user — is a Server Action.
How does the home page fetch data without an API call?
The home page is a Server Component (the default for anything in app/ without "use client"). It runs only on the server, so it can await Prisma queries directly in the component body — getFeaturedPosts(), getLatestPosts(), getFeaturedWriters() are called in parallel with Promise.all, and the resulting HTML is what gets sent to the browser. No client-side fetch, no loading spinner for the initial render.
What does revalidatePath do and why is it needed after every mutation?
Next.js caches server component output. After a mutation — publishing a post, adding a comment — the cached version of the affected page would still show stale data on the next visit. revalidatePath("/articles/my-slug") marks that path's cache as stale, so the next request re-runs the server component and re-fetches from the database. Actions here typically call it once, sometimes more than once, when a mutation affects more than one route (e.g. publishing invalidates the article page, the author's profile, and the home page).
What are route groups and why does this app use two of them?
Route groups are folders in parentheses — (auth) and (main) here — that organize files without affecting the URL: (auth)/login/page.tsx still resolves to /login, not /auth/login. This project uses (auth) for login/signup so they can share a minimal layout with no header/footer, and (main) for the public site so home/discover/articles/profiles share the full site chrome — without either group's URL structure implying the grouping exists.

Interview Q&A — Authentication

Why split the auth config into two files instead of one?
Middleware runs in the Edge runtime, a lightweight V8 isolate that doesn't support Node.js built-ins. bcryptjs and Prisma's adapter both require Node.js APIs, so neither can be imported anywhere in the module graph that middleware touches — even transitively. edge-config.ts contains only the JWT/session callback shape and page routes, with an empty providers: [], and is the only auth module middleware imports. config.ts is the full config — Prisma adapter, Credentials provider with bcrypt, OAuth providers — used everywhere else. If bcrypt were imported anywhere in middleware's chain, the build would fail or the Edge function would crash at runtime.
Why rate-limit inside the authorize() callback specifically?
Putting the check inside authorize() means a rate-limited login attempt returns exactly the same result as a wrong password — NextAuth's generic "invalid credentials" failure. If rate-limiting lived as a separate check before signIn() was even called, a distinct error message ("too many attempts") would tell an attacker they'd found a real, existing account being actively targeted — a minor but real information leak avoided by keeping both failure modes indistinguishable to the client.
Why use JWT sessions instead of database sessions here?
JWT sessions store the user's id/role/username in a signed cookie — reading a session on every request is just a signature check, not a database round-trip. Database sessions require a lookup on every request to validate the session id. Given the app already re-verifies authorization inside every sensitive server action (see the Security Q&A), the session's only job is answering "who is this," and a fast, stateless check is the right tool for that.
How does username end up on session.user without a query on every request?
It's added once, at sign-in, inside the jwt() callback — which only runs when the user parameter is present (i.e., on login, not on every token refresh). It looks up the user's Profile.username and stores it on the token. Every subsequent request's session() callback just copies it from the already-signed token onto session.user — no database call happens on ordinary requests, only at the moment of login.

Interview Q&A — Database & Prisma

Why does Prisma need a singleton in Next.js dev?
Next.js dev's Hot Module Replacement re-evaluates a changed module (and everything importing it) on every save. Without a singleton, each re-evaluation would create a brand-new PrismaClient with its own connection pool — and Postgres has a connection limit that a handful of file saves would exhaust. Storing the instance on globalThis works around this because globalThis itself is not re-evaluated by HMR the way module-scoped variables are; the existing instance is found and reused instead of a new one being created. In production, modules are only evaluated once, so the guard is a no-op there.
How does soft-deleting a comment avoid orphaning its replies?
The naive approach — filtering isDeleted: false on every comment query — would make a deleted parent comment vanish from the result set entirely, and since replies are only fetched nested inside their parent's query, any live replies underneath it would become unreachable even though they're still in the database. The fix filters after the fetch instead of in the where clause: a comment is only dropped from the result if it's deleted and none of its replies are still live. Otherwise it stays in the list and the UI renders it as a [deleted] tombstone, with its live replies rendered normally underneath.
Why is PostTag's primary key a composite of (postId, tagId) instead of its own id column?
It's a pure join table — a row's entire meaning is "this post has this tag," which is exactly the uniqueness a composite primary key on (postId, tagId) already enforces at the database level. A separate auto-generated id would add nothing except the possibility of two rows representing the same post-tag pair, which the app would then have to prevent manually. The composite key is also what the tag-sync logic targets directly in its delete calls — where: { postId_tagId: { postId, tagId } } — so it doubles as a natural, efficient lookup key.
Why wrap the comment-count increment in a transaction with the comment insert?
Without a transaction, it's possible for the comment insert to succeed and the count increment to fail (or vice versa, or the process to crash between the two) — leaving post.commentCount permanently out of sync with the actual number of comments, with nothing in the system positioned to ever notice or correct it. db.$transaction(async (tx) => {...}) makes both writes atomic: either the comment exists and the count went up, or neither happened. The same pattern is used for like counts, follow counts, and tag usage counts — anywhere a denormalized counter exists alongside the rows it's counting.

Interview Q&A — Patterns & Architecture

Why is the codebase organized by feature instead of by file type?
A type-based layout (one top-level components/, one actions/, one hooks/ for the whole app) means every new feature touches several unrelated top-level folders, and finding everything related to, say, comments means searching across all of them. Here, features/comments/ owns its own actions/, components/, schemas/, and services/ — everything related to one domain lives in one place, and adding a feature means adding a folder, not editing five existing ones. Cross-cutting UI primitives (buttons, dialogs) still live in a shared top-level components/ui/, since those genuinely aren't feature-specific.
What is useTransition doing in the optimistic-update pattern here?
useTransition returns [isPending, startTransition] and marks the wrapped state update as a non-urgent background transition. In the like/bookmark/follow toggles, the visible state flips synchronously and immediately (outside the transition), then the actual server action call is wrapped in startTransition — so the UI never blocks waiting for the network, isPending is available to disable the button against double-clicks, and if the action throws, the catch block flips the state back to what it was before the optimistic update.
Why does every AI-assist action parse the model's response defensively instead of trusting the prompt's instructions?
A system prompt asking for "exactly 5 tags, comma-separated, no commentary" is a strong hint, not a contract — the model can still wrap the answer in a sentence, add a leading dash, or return 4 or 6 items. Every AI action here treats the raw string as untrusted text: splitting, trimming, stripping leading punctuation/numbering, filtering empties, and capping the array length, before ever handing it back to the client. If that cleanup still yields nothing usable, the action throws a clear "try again" error instead of silently returning an empty or malformed result.
Why diff the tag list on save instead of just deleting and recreating all tags every time?
The editor autosaves every ~8 seconds, and a delete-everything/recreate-everything approach would run Tag.usageCount increments and decrements on every single tick regardless of whether the tags actually changed — inflating and then correcting counts constantly, and doing far more database writes than necessary. Diffing against the currently-stored tags first (toAdd/toRemove as set differences) means an autosave where the tags are unchanged does zero tag-related writes at all, and usageCount only moves when a tag genuinely gains or loses this post.

Interview Q&A — Security

What are the main security measures in this application?
Authentication: protected routes gated by Edge middleware; every server action independently re-reads the session from the signed JWT cookie rather than trusting anything in the request body.

Authorization: every mutating server action checks ownership or role before doing anything — e.g. deleting a comment checks comment.authorId === session.user.id, admin actions check role === "ADMIN".

SQL injection: Prisma parameterizes every query; user input is never interpolated into SQL strings.

XSS: editor-produced HTML is run through rehype-sanitize server-side before ever being set via dangerouslySetInnerHTML.

Password storage: bcryptjs, 12 rounds, random salt per user.

Rate limiting: login (5/15 min per email) and signup (5/hour per IP) both throttled server-side.

Upload auth: UploadThing's .middleware() rejects unauthenticated requests before a presigned URL is ever issued — not just a hidden button client-side.
Why does a server action re-check ownership even though middleware already protects the route?
Middleware protects a page's URL — it answers "is this person allowed to load this page at all." It says nothing about which specific resource a subsequent action targets. /new-post/[id] is reachable by any signed-in user; the page itself (and, more importantly, savePostDraftAction/publishPostAction) is what checks that the loaded post's authorId actually matches the current session. Without that second check, any signed-in user could edit or publish anyone else's draft simply by knowing its id — the URL being "protected" wouldn't have stopped that.
Why is sanitizing the editor's HTML server-side necessary if only the author who wrote it can edit it?
Sanitization isn't primarily defending against the author attacking themselves — it's defending every other visitor who loads that article and has that HTML injected into their DOM via dangerouslySetInnerHTML. If a writer's account is compromised, if a future paste-from-clipboard feature lets raw HTML through, or if any client-side code path that produces the stored HTML has a bug, unsanitized output would mean a stored XSS payload served to every single reader of that article — not just the author. Sanitizing on the server, right before rendering, means the trust boundary is enforced in exactly one place regardless of how the HTML was produced.
Why does rate-limiting live inside authorize() instead of returning a distinguishable error?
Returning null from authorize() makes a rate-limited attempt indistinguishable from a wrong password to the client — both produce NextAuth's generic CredentialsSignin failure. If the app instead surfaced "too many attempts, try again in 10 minutes" as a distinct message, an attacker probing a list of emails could use that response to confirm which addresses correspond to real accounts currently being brute-forced, and which don't exist at all. Collapsing both failure modes into one generic message costs a small amount of UX clarity in exchange for not leaking account-enumeration information.
